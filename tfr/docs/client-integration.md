# Спецификация для C++-стороны: pull-first клиент, `sync.push` как дополнение

Статус: **спецификация, не реализация.** C++ не менялся ни на строку
(`tdesktop/**`, `CMakeLists.txt`, `cmake/**`, `.gitmodules` не тронуты).
Документ согласован с уточнённой архитектурой («сервер — источник, клиент —
читатель», см. § 2); серверная половина протокола — [`transport.md`](transport.md).

> **Что изменилось после уточнения заказчика.** Раньше этот документ описывал
> клиент как основной источник событий (`sync.push` из C++). Теперь основной
> источник — **агент на сервере**: он подключён к общей БД (PostgreSQL/MySQL, как
> `teleforge_ssh_tunnel.cpp`), читает изменения, шифрует их DEK-ом аккаунта и
> публикует. Клиент в первую очередь **читает** (`sync.pull`). `sync.push`
> остаётся только для того, чего в БД нет.

## 2. Два режима синхронизации

```
[общая БД на сервере: PostgreSQL / MySQL]      ← источник истины, как сейчас
        │  SELECT по монотонному курсору
        ▼
[teleforge-agent на сервере]                   ← читает, шифрует DEK-ом аккаунта,
        │                                       шардирует, публикует
        │  ops (append-only журнал, op_seq)
        ├──────────────────────► [облако / канал: зашифрованные шарды]
        │
        ▼  sync.pull  (клиент читает страницы по op_seq)
[C++ клиент]  ── применяет к локальной БД, показывает «требует решения» при 409/конфликте
        │
        └── sync.push (дополнительно) ──► только то, чего в БД нет
```

| | **Server-side sync** (основной) | **Client-side push** (дополнительный) |
|---|---|---|
| Источник данных | общая БД пользователя | клиент |
| Кто пишет в журнал `ops` | агент (читает БД, шифрует, публикует) | клиент через `sync.push` |
| Что переносится | всё, что есть в БД: сообщения (включая правки/удаления), присутствие, профили, архивные наблюдения | ghost-настройки, «прочитано в госте», локальные флаги, которых в БД ещё нет |
| Триггер | периодический опрос БД по курсору (плюс `db.status` для наблюдаемости) | событие в клиенте |
| Основной вызов клиента | `sync.pull` (+ `sync.stamp`, `sync.conflicts`) | `sync.push` (+ `sync.pull` для подтверждения) |
| Права | у агента: `SELECT` на нужные таблицы, `INSERT/UPDATE` только на курсор/outbox | у клиента: токен со scope `sync:write` |
| Отказ агента или БД | клиент работает локально и показывает статус | локальная запись не зависит от агента (правило dual-run) |

**Следствия, которые нельзя потерять при реализации:**

1. `sync.pull` должен содержать **всё**, что клиенту нужно для сходимости. Push
   не является обязательным путём, поэтому «клиент не отправил → данные
   потерялись» недопустимо для данных, которые есть в БД.
2. Push и серверный ingest могут описать **один и тот же** факт двумя путями.
   У них разный `device_id` и разный HLC, поэтому `content_hash` (в котором
   device_id не участвует, но HLC участвует) **не совпадёт**, и это будет
   выглядеть как конфликт, а не как дубликат. Политика по умолчанию:
   * клиент пушит **только то, чего в БД нет** (иначе — конфликт, который
     человек увидит);
   * для фактов, которые есть в БД, источником считается сервер. Как агент
     должен вычислять `content_hash` для DB-строк, чтобы клиентский повтор
     схлопнулся в `duplicate`, — открытый вопрос § 12.1.
3. Шифрование на сервере меняет модель доверия: агент теперь держит DEK и видит
   plaintext строк, которые читает из БД. Подробно — `transport.md` § 1.3;
   это решение заказчика и его нужно подтвердить явно (§ 12.2).

## 3. Контракт «клиент → агент»

### 3.1 Транспорт

```
POST https://127.0.0.1:<port>/rpc  (через SSH-форвард; unix-socket — позже)
TLS 1.3, сертификат агента проверяется по пиннингу (SHA-256 от DER)
Authorization: Bearer <device_token>
Content-Type: application/json
Connection: close            ← сервер закрывает соединение после одного ответа
```

Требования к клиенту:

1. **Пиннинг.** `QSslCertificate::digest(QCryptographicHash::Sha256)` от
   сертификата, который показал агент при установке
   (`status.listener_fingerprint`). Никакого «доверять всем»: иначе MITM на
   loopback-порту читает токен.
2. **Один запрос на соединение.** Не кэшировать сокет между вызовами: сервер
   отвечает `Connection: close`.
3. **Таймауты.** `connect` 3 с, `read/write` 10 с; при таймауте — ретрай с
   backoff, а не вечное ожидание на UI-потоке.
4. **Поток.** Вызовы только из одного sync-потока (или `crl::async` с
   собственным таймером), никогда с UI-потока: `sync.pull` страницы и
   `sync.push` батча — сетевые вызовы на секунды.
5. **Отмена.** `abort()` при shutdown, чтобы закрытие приложения не ждало 10 с.
6. **Батч и страница ≤ 8 МиБ** (`max_body_bytes`); `sync.push` ≤ 2000 событий,
   `limit` страницы зажимается сервером в `1..=2000`.

### 3.2 Аутентификация

Токен — 32 случайных байта, hex (64 символа), выдаётся **один раз** командой
`teleforge-agent pair` и хранится в OS keychain:

```
Authorization: Bearer e8ae9c5011f5455b3b788e7b9cb3905e4fbc2aa11dd4aca95b0c30fd367ab657
```

Клиент **не** присылает `device_id` в батче: агент подставляет его из токена.
Токен привязан к `tenant` + `account`; запрос с другим аккаунтом — `403`.

Это токен **читателя**. Доступ к БД — отдельная учётная запись, которая к
токену клиента отношения не имеет (§ 4).

### 3.3 Порядок запуска

Клиент не включает синхронизацию, пока не проверил три вещи (подробный контракт
методов — `transport.md` § 5.1, § 5.2, § 5.8):

```
1. hello          (без токена)   агент жив, версия и окно протокола
2. status         (токен)        vault, components, listener_fingerprint
3. db.status      (токен)        агент подключён к БД, курсор, lag
   ↓ только если все три зелёные
4. sync.stamp     → high_water, откуда тянуть
5. sync.pull      страницами до has_more == false
```

Правила:

| Ситуация | Поведение клиента |
|---|---|
| `hello` не отвечает / таймаут | локальный режим, статус «агент недоступен», синхронизация выключена; ретрай с backoff |
| `hello` ок, `status` даёт `vault: "locked"` | **pull разрешён**: журнал хранит шифртекст, DEK для чтения не нужен; в UI — «агент заперт, обновления подтягиваются» |
| `status` ок, `db.status.connected == false` | синхронизация **выключена**, в UI — «агент жив, БД недоступна»; pull можно не запускать, данных нет |
| `db.status.lag_ms` растёт | показать «синхронизация отстаёт», не блокировать чтение |
| `401` на `status`/`db.status` | токен недействителен → KillSwitch (`legacy`), UI «перепривяжите устройство» |
| `501` на `db.status` (старая сборка агента) | считать БД-контур неизвестным: остаться в локальном режиме и предложить обновить агент |

Почему `db.status` — отдельный вызов, а не поле `status`: `status` должен
отвечать, даже когда БД недоступна (иначе клиент не отличит «агент мёртв» от
«агент жив, БД лежит»), а `db.status` делает реальный дешёвый запрос к БД
(`SELECT 1` + чтение курсора) и потому может быть медленным или недоступным.

## 4. Права БД для агента (чеклист установщика)

Полный текст с SQL — [`transport.md`](transport.md), раздел «Права БД для
агента». Здесь только то, что обязан проверить/создать установщик и показать в
UI:

1. **Отдельный пользователь БД**, не `root`, не суперюзер, не владелец схемы:
   `teleforge_agent` (PG) / `'teleforge_agent'@'127.0.0.1'` (MySQL).
2. **Только нужные таблицы и только нужные колонки.** Никакого
   `GRANT ALL ON *.*`, `pg_read_all_data`, `SUPER`, `CREATE`, `DROP`, `ALTER`,
   `GRANT OPTION`.
3. **Никакого доступа к таблицам секретов** (`personality_core`,
   `openai_api_key`, конфиги с `pgConnString`/`ssh*`).
4. **Креды — в keystore, не в `agent.toml`.** `agent.toml` — `0640` и не должен
   содержать пароль (это ровно M14 из аудита). Клиент передаёт пароль при
   `unlock`/`init` по SSH-каналу, агент кладёт его в vault и больше не отдаёт.
5. **TLS или SSH-туннель.** `sslmode=verify-full` (PG) / `tls=true` + CA (MySQL)
   **или** подключение через `ssh -L`/`russh` с пиннингом host key
   (`StrictHostKeyChecking=yes`, известный fingerprint). Открытый `pg_hba` без
   TLS — отказ, а не предупреждение.
6. **Проверка до подключения.** Установщик (или `teleforge-agent db-check`,
   когда появится) выполняет `SELECT 1` + `SELECT <cursor column> … LIMIT 1`.
   Если прав нет — установка не должна идти дальше «агент поставлен, но
   синхронизация не работает».
7. **UI.** Показывать три состояния: «БД доступна, курсор N», «БД недоступна
   (текст ошибки без кредов)», «права недостаточны (какая таблица)».

Что клиент **не** делает: он не подключается к БД напрямую в этом контуре и не
хранит её креды.

## 5. Структуры на стороне C++

### 5.1 `Agent::PulledOp` (то, что клиент читает)

```cpp
namespace TeleForge::Agent {

struct PulledOp {
    quint64  opSeq        = 0;     // монотонный курсор
    quint8   kind         = 0;     // 1..7, см. EventKind
    QString  entityId;             // "message:<dialog>:<msg>" | ...
    QString  field;                // пусто там, где поля нет
    QByteArray valueCt;            // БАЙТЫ значения (AEAD-конверт) — после fromBase64
    quint64  hlcPhysical  = 0;
    quint16  hlcLogical   = 0;
    QString  deviceId;             // "server-db" для серверного ingest'а или hex устройства
    QByteArray contentHash;        // 32 байта
    qint64   appliedAtMs  = 0;
};

} // namespace TeleForge::Agent
```

Порядок применения: строго по `op_seq`; запись «последний применённый op_seq» —
в локальную БД **в той же транзакции**, что и применение страницы, иначе crash
между ними перечитает страницу (это безопасно, но лучше не перечитывать).

### 5.2 `Agent::Event` (только для push того, чего нет в БД)

```cpp
struct Event {
    EventKind kind;
    QString   entityId;
    QString   field;          // "" там, где поле запрещено (delete/presence)
    QByteArray value;         // БАЙТЫ значения; для sync-данных — AEAD-конверт
    Hlc       hlc;            // см. § 5.5
    QByteArray contentHash;   // 32 байта, sha256; § 5.6
};
```

Правила `entity_id` (парсер сервера строгий, `entity_id` ≤ 128 байт):

| `kind` | `entity_id` | `field` | `value` |
|---|---|---|---|
| `MessageNew`/`MessageEdit` | `message:<dialog_id>:<message_id>` | обязателен, из 18 имён | байты поля (AEAD) |
| `MessageDelete` | то же | **запрещён** | пусто |
| `PresenceOnline`/`Offline` | `presence:<peer_id>` | запрещён | ровно 8 байт BE `i64` |
| `ProfileUpdate` | `profile:<peer_id>` | обязателен, из 8 имён | ≤ 4 КиБ |
| `ArchiveObservation` | `archive:<peer_id>` | обязателен, из 5 источников | ≤ 8 КиБ |

Имена полей — закрытые наборы (опечатка → отказ, а не новая история):

```
message: text entities edit_date views media media_path mime_type document thumbs
         attributes reply reply_markup post_author fwd_name fwd_post_author
         grouped_id topic_id flags
profile: first_name last_name username bio userpic_path chat_title
         self_in_chat still_in_chat
archive: new_message forward_author participant opened_chat profile_update
```

> Эти же «18/8/5» имён и `entity_id` использует **серверный** ingest, когда
> читает БД. Клиент обязан использовать ту же схему имён для локальных данных,
> иначе один факт получит два разных адреса.

### 5.3 Соответствие локальным таблицам C++

| Таблица C++ | `kind` | `field` | Кто источник |
|---|---|---|---|
| `DeletedMessage` / `EditedMessage` | `MessageDelete` / `MessageEdit` | `text` (+ `entities`, `edit_date`, …) | **сервер** (из БД) |
| `OnlineEvent` | `PresenceOnline`/`Offline` | — (`onlineTill`/`lastSeen` в payload) | **сервер** |
| `PeerArchiveName` | `ProfileUpdate` | `first_name`, `last_name` | **сервер** |
| `PeerArchiveUsername` | `ProfileUpdate` | `username` | **сервер** |
| `PeerArchiveBio` | `ProfileUpdate` | `bio` | **сервер** |
| `PeerArchiveChatMembership` | `ProfileUpdate` | `chat_title`, `self_in_chat`, `still_in_chat` | **сервер** |
| автор/участник чата | `ArchiveObservation` | `forward_author`, `participant`, `opened_chat` | **сервер** |
| ghost-настройки, «прочитано в госте», локальные флаги | см. § 12.3 (нужен закрытый список полей) | — | **клиент (push)** |
| `MemoryItem` | — | **не синхронизируется** в этом шаге: ключ `contentHash`, не `id` (H7) | — |
| `PersonalityCore` | — | **не синхронизируется никогда**: `openAiApiKey`, `pgConnString` (C2) | — |

### 5.4 JSON одного события (push)

```json
{"kind":"message_edit",
 "entity_id":"message:-1001234567890:42",
 "field":"text",
 "value":"aGVsbG8gZWRpdGVk",
 "hlc":"0000018f3c1a2b40-0000",
 "content_hash":"9f0e…64 hex…"}
```

* `value` — **base64** (стандартный алфавит, `=`-паддинг, без переводов строк);
* `hlc` — `"%016llx-%04x"` (physical_ms, logical) или объект
  `{"physical_ms":N,"logical":M}`;
* `content_hash` можно не присылать — сервер посчитает сам (§ 5.6).

### 5.5 HLC (обязательно монотонный на устройство)

Агент отвергает событие с `hlc <= последнего HLC этого устройства`
(`rejected: non_monotonic_hlc`):

```
tick():
  now = wall_clock_ms()
  if now > last.physical:  last = { now, 0 }
  else:                    last.logical += 1        // logical ≤ 65535
  return last
```

Серверный ingest ведёт **свой** `device_id` (предлагаемое имя — `server-db`) и
свою монотонность; клиентские push-события идут под своим `device_id` из токена,
поэтому два пути не ломают часы друг друга.

### 5.6 `content_hash` (точный алгоритм)

32 байта, `SHA-256` от конкатенации:

```
"tf/passive/event/v1\0"          14 байт, с завершающим NUL
kind_code                        u8, 1..7
len(entity_id)  u32 BE           + entity_id (UTF-8)
field_tag        0x00 | 0x01     + [len(field) u32 BE + field] при 0x01
hlc.encode()                     10 байт: u64 BE physical + u16 BE logical
len(value) u64 BE                + value
```

```cpp
QByteArray ContentHash(const Agent::Event &e) {
    QCryptographicHash h(QCryptographicHash::Sha256);
    h.addData("tf/passive/event/v1", 21);   // 21 = strlen, включая NUL
    h.addData(QByteArray(1, char(e.kind)));
    const auto id = e.entityId.toUtf8();
    h.addData(Be32(id.size()));
    h.addData(id);
    if (e.field.isEmpty()) {
        h.addData(QByteArray(1, '\0'));
    } else {
        const auto f = e.field.toUtf8();
        h.addData(QByteArray(1, '\1'));
        h.addData(Be32(f.size()));
        h.addData(f);
    }
    h.addData(Be64(e.hlc.physicalMs) + Be16(e.hlc.logical));
    h.addData(Be64(e.value.size()));
    h.addData(e.value);
    return h.result();                       // 32 байта
}
```

Golden vectors — § 11.

### 5.7 Значение (`value`)

* `value` — **AEAD-конверт**: `subkey(DEK, LABEL_SYNC_DATA)`, AAD =
  `entity_key || field_id || tombstone`; агент его не открывает при `pull`;
* тот же DEK и та же метка используются серверным ingest'ом, когда он шифрует
  строки, прочитанные из БД (`transport.md` § 1.3). Поэтому клиент расшифровывает
  и «свои» (push) и «серверные» значения одним ключом;
* клиент обязан сохранять `key_id` из конверта и не пере-запечатывать чужие
  значения.

## 6. Вызовы

### 6.1 `sync.pull` — основной путь

```json
{"protocol":1,"request_id":"<ulid>","method":"sync.pull",
 "params":{"tenant":"<hex32>","account":"<hex32>","since_seq":<N>,"limit":200}}
```

* курсор `since_seq` хранится в локальной БД;
* `next_seq` → следующий `since_seq`; `has_more` → продолжать без паузы;
* **`409`** — `since_seq > high_water` (агент о другом сторе) **или** курсор ниже
  pruned-границы. Реакция: `sync.stamp`, сброс курсора, показ «нужна полная
  сверка»; не ретраить с тем же курсором;
* `value` — base64; `fromBase64` → конверт → расшифровка DEK-ом клиента.

### 6.2 `sync.push` — только локальные данные

```json
{"protocol":1,"request_id":"<ulid>","idempotency_key":"<тот же ulid>",
 "method":"sync.push",
 "params":{"tenant":"<hex32>","account":"<hex32>","ops":[ Event, … ]}}
```

Правила:

1. **Не пушить то, что есть в БД.** Иначе тот же факт придёт вторым путём с
   другим HLC и станет конфликтом (см. § 2, следствие 2).
2. `idempotency_key` — один ULID на батч; ретрай того же батча — тот же ключ.
3. Ответ содержит `results` с `rejected`/`duplicates` — разбирать, а не смотреть
   только на HTTP 200.
4. Ошибка push не влияет на локальную запись (правило dual-run).

Полный формат ответа — `transport.md` § 5.3.

### 6.3 `sync.stamp`

Дешёвый «насколько я отстал»: `high_water`, `last_write_ms`, `op_count`.
Использовать вместо `PgFetchRemoteStamp` (полный скан датасета).

### 6.4 `sync.conflicts`

```json
{"protocol":1,"request_id":"<ulid>","idempotency_key":"<ulid>",
 "method":"sync.conflicts",
 "params":{"tenant":"<hex32>","account":"<hex32>","since_id":0,"limit":100,
           "resolve":[{"conflict_id":3,"resolved_by":"device-hex"}]}}
```

Показывать в UI как «требует решения», без автовыбора (H7). Конфликты возможны
между серверными (из БД) и клиентскими (push) записями одного поля — это
ожидаемо и должно быть видимо.

### 6.5 `sync.prune`

Только когда все устройства применили ≥ N. `409` = агент не выдавал такой
`op_seq` → перечитать `sync.stamp`.

### 6.6 `hello` / `status` / `db.status`

`hello` — без токена. `status` — с токеном (vault, components,
`listener_fingerprint`). `db.status` — подключение к БД и курсор
(`transport.md` § 5.8); реализован (агентом сборки `0.1.0+`, см.
[`db-ingest.md`](db-ingest.md)), но клиент обязан сохранять поведение из § 3.3:
`501` от старой сборки означает «состояние БД неизвестно», а не ошибку.

### 6.7 `shutdown`

Перед заменой бинарника (шаг updater). После него systemd перезапускает агент.

## 7. Обработка ошибок

| HTTP | `error.code` | Причина | Что делает клиент |
|---|---|---|---|
| `400` | 1000 | битый JSON, кривая форма `ops`, нет `idempotency_key` | не ретраить; баг клиента, лог с `request_id` |
| `400` | 1001 | `protocol` вне окна | «обновите клиент/агент», выключить агент |
| `401` | 1002 | токена нет/неверный/отозван | KillSwitch (`legacy`), «перепривяжите устройство» |
| `403` | 1003 | чужой аккаунт/тенант, нет scope | не ретраить; ошибка конфигурации |
| `403` | 1004 | vault заперт для метода, которому нужен DEK | `sync.pull` этого не требует; для `db.*` — попросить `unlock` |
| `409` | 1006 | курсор/версия/pruned-граница | сброс курсора по `stamp`, полная сверка |
| `429` | 1007 | rate limit | ретрай с backoff, не раньше ~1 с |
| `413` | — | тело больше лимита | уменьшить страницу/батч |
| `500` | 1099 | ошибка хранилища/TLS у агента | 2–3 ретрая с backoff, затем KillSwitch |
| `501` | 1099 | метод не реализован в этой сборке | не ретраить; `db.status` → «состояние БД неизвестно» |
| сеть | — | таймаут/обрыв | ретрай с backoff |

Правила: ретраить только `429`/`500`/сеть и только с тем же
`idempotency_key`; на `401`/`403`/`501` — никогда. `request_id` из ответа всегда
писать в лог рядом с ошибкой.

## 8. Что клиенту нужно знать про агента

| Значение | Откуда взять | Куда |
|---|---|---|
| `tenant` | `init`/`meta.json` при установке | параметр каждого `sync.*` |
| `account` | hex32 от агента (не `userId`) | параметр каждого `sync.*` |
| `device_token` | `pair` (один раз) → OS keychain | `Authorization: Bearer` |
| fingerprint сертификата | `status.listener_fingerprint` | проверка TLS |
| `high_water`, курсор | `sync.stamp` / `sync.pull` | прогресс в UI, `since_seq` |

локальной БД.

## 9. Порядок внедрения (шаги migration.md)

| Шаг | Что делает клиент | Что нужно на сервере |
|---|---|---|
| 3 (`shadow`, **pull-first**) | `hello`→`status`→`db.status`→`sync.stamp`; `sync.pull` со `since_seq=0`, сравнение с локальной БД, **только лог**; push ещё выключен | **новое:** чтение БД по курсору, шифрование, `db.status` (сейчас нет) |
| 4 (`dual-write`) | `sync.pull` применяется к локальной БД; конфликты в `AgentConflict`; `Agent::ShadowIngest` для локальных данных | то же + `prune_upto`, импорт старых `TFSYNC1` |
| 5 (`primary`) | `sync.pull` — единственный путь чтения; push — только локальные факты; старые бэкенды deprecated | публикация зашифрованных шардов в облако/канал |

Важно: шаг 3 в pull-first варианте **не требует** ни одной правки в C++-модели
данных — только чтение и сравнение. Это делает его безопасным первым шагом.

## 10. Критерии приёмки для C++-части

1. **Pull-first:** клиент без единого `push` сходится с БД-контуром: после
   `sync.pull(since_seq=high_water)` и `sync.pull(since_seq=0)` набор сущностей
   совпадает с тем, что агент прочитал из БД (сверка по `entity_id`+`field`,
   значения — после расшифровки).
2. **Порядок запуска:** при `db.status.connected == false` синхронизация не
   включается, UI показывает причину; при `401` — KillSwitch; при `501` на
   `db.status` — «неизвестно», локальный режим.
3. **Идемпотентность push:** тот же батч дважды → `applied: 0`, `duplicates: N`;
   `sync.stamp.op_count` не меняется.
4. **HLC:** событие с HLC ≤ предыдущего от того же устройства → `rejected:
   non_monotonic_hlc`, остальные события батча применяются.
5. **409:** курсор за `high_water` и курсор ниже pruned-границы → сброс курсора и
   полная сверка, **без** потери локальных записей.
6. **Пагинация:** 5000 операций за ≤ 5 с на 1 vCPU (страницы по 200).
7. **Offline:** агент выключен на 30 минут — локальная запись продолжается, после
   включения догон без потерь; KillSwitch за ≤ 5 попыток.
8. **Секреты:** токен и `value` не появляются в логах ни на одном уровне;
   DB-креды не попадают ни в `agent.toml`, ни в лог.
9. **Конфликт виден:** серверная и локальная записи одного поля → `sync.pull`
   отдаёт обе, `sync.conflicts` показывает пару, UI не выбирает победителя сам.
10. **Пиннинг:** подмена сертификата агента → соединение отклоняется.
11. **Лимиты:** страница `limit=2000` и батч ровно 2000 событий проходят; больше
    — `400`/`413`, клиент режет и повторяет.

## 12. Открытые вопросы к заказчику и владельцу C++-части

1. **`content_hash` для DB-строк.** Сейчас hash включает HLC, а HLC для
   server-side ingest генерирует агент. Если клиент пушит тот же факт, что уже
   прочитан из БД, hash не совпадёт → конфликт. Варианты: (а) клиент пушит только
   локальные факты (выбрано по умолчанию); (б) агент для DB-строк использует
   hash, выводимый из стабильных полей строки (`dialog_id/message_id/updated_at`),
   чтобы клиентский повтор схлопывался; (в) конфликт — норма, показывать в UI.
   Нужно решение до шага 4.
2. **Модель доверия.** Серверный ingest означает, что агент держит DEK и видит
   plaintext строк БД; «агент видит только метаданные» (§ 7.6 `architecture.md`)
   для DB-происходящих данных больше не верно, хотя облако/канал по-прежнему
   получают только шифртекст. Подтвердить, что это приемлемо, и обновить
   `architecture.md` § 7.6/§ 10.7.
3. **Локальные «ghost»-данные.** Какие именно поля пушить: `ghost_mode`,
   `read_in_ghost`, локальные флаги? Нужен закрытый список `field`-имён (сейчас
   сервер знает только 18/8/5 имён из `MESSAGE_FIELDS`/`PROFILE_FIELDS`/
   `ARCHIVE_SOURCES`), иначе push локального поля будет `unknown_field`.
4. **Кто создаёт `account`.** Сервер должен создать его при первом ingest из БД
   или клиент передаёт hex при `pair`? Сейчас `pair --account` требует готовое
   значение.
5. **Имя серверного устройства.** Предлагается `device_id = "server-db"`;
   клиент должен уметь отличать серверные записи от своих (для UI «источник:
   сервер/устройство») — подтвердить имя.
6. **`prune` и несколько устройств.** Кто считает минимум курсора — клиент
   (передаёт явный `upto_seq`) или агент ведёт `device_cursor` и запрещает
   слишком ранний `prune`? Сейчас клиент, явно.
7. **UI при pruned-курсоре.** `409` с указанием границы — достаточно, или нужен
   отдельный код «требуется полная пересборка локальной БД»?
8. **Облако/канал.** Кто публикует шарды (агент, отдельный шаг updater'а) и
   нужен ли клиенту вообще облачный путь, если он стоит рядом с сервером и
   может тянуть `sync.pull`? Это влияет на шаг 5 и должно быть решено до него.
9. **Точная схема облачной БД, которую читает агент.** В `transport.md` § 2.6
   таблицы/колонки (`messages`, `deleted_messages`, `online_events`,
   `peer_archive_*`, `sync_outbox`, …) приведены как **пример**: реальная схема
   определяется тем, что пишет клиент в PostgreSQL/MySQL. Нужен зафиксированный
   список таблиц и колонок (и решение по outbox/курсору) — без него нельзя ни
   выдать `GRANT`, ни реализовать чтение.
